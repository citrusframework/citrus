[[runtimes-cucumber]]
== Cucumber

Behavior driven development (BDD) is a very popular concept when it comes to find a common understanding of test scopes
test logic. The idea of defining and describing the software behavior as basis for all tests in prior to translating those
feature descriptions into executable tests is a very interesting approach because it includes the technical experts as well
as the domain experts.

With BDD the domain experts should be able to read and verify tests and the technical experts get a detailed description
of what should happen in the test.

The test scenario descriptions follow the Gherkin syntax with a *"Given-When-Then"* structure. The Gherkin language is
business readable and helps to explain business logic with help of concrete examples.

There are several frameworks in the Java community supporting BDD concepts. Citrus has dedicated support for the Cucumber
framework because Cucumber is well suited for extensions and plugins. So with the Citrus and Cucumber integration you can
write Gherkin syntax scenarios in order to run those as Citrus integration tests.

NOTE: The Cucumber components in Citrus are located in a separate Maven module. You need to include the module as a Maven
dependency to your project.

.Cucumber module dependency
[source,xml]
----
<dependency>
  <groupId>org.citrusframework</groupId>
  <artifactId>citrus-cucumber</artifactId>
  <version>${citrus.version}</version>
</dependency>
----

Citrus runs Cucumber through the JUnit Platform. The Cucumber JUnit Platform engine executes the feature files and
integrates with the Citrus object factory and glue code. So following from that we need Maven dependencies for the
JUnit Platform engine and the JUnit Platform suite support:

.Cucumber JUnit Platform support
[source,xml]
----
<dependency>
  <groupId>io.cucumber</groupId>
  <artifactId>cucumber-junit-platform-engine</artifactId>
  <version>${cucumber.version}</version>
</dependency>
<dependency>
  <groupId>org.junit.platform</groupId>
  <artifactId>junit-platform-suite</artifactId>
  <version>${junit.platform.version}</version>
</dependency>
----

The `junit-platform-suite` artifact provides the `@Suite` annotation and the suite engine that delegates test discovery
to the Cucumber engine.

In order to enable Citrus Cucumber support we need to specify a special object factory in the environment. The most
comfortable way to specify a custom object factory is to add this property to the `junit-platform.properties` in classpath.

.junit-platform.properties
[source,properties]
----
cucumber.object-factory=org.citrusframework.cucumber.backend.CitrusObjectFactory
----

NOTE: The JUnit Platform Cucumber engine reads `junit-platform.properties`. The `cucumber.properties` file is still
supported when running Cucumber through the Citrus test engine or the Cucumber command line.

This special object factory takes care of creating all step definition instances. The object factory is able to inject
`@CitrusResource` annotated fields in step classes. We will see this later on in the examples. The usage of this special
object factory is mandatory in order to combine Citrus and Cucumber capabilities.

The *CitrusObjectFactory* will automatically initialize the Citrus world for us. This includes the default Citrus context
configuration that is automatically loaded within the object factory. So you can define and use Citrus components as usual
within your test.

After these preparation steps you are able to combine Citrus and Cucumber in your project.

TIP: In case you want to use Spring support in Citrus with a Spring application context you should use the following factory
implementation.

.junit-platform.properties
[source,properties]
----
cucumber.object-factory=org.citrusframework.cucumber.backend.spring.CitrusSpringObjectFactory
----

[[cucumber-options]]
=== Cucumber options

Cucumber runs on the JUnit Platform. The basic test case is an empty suite class that selects the feature files and
configures the Cucumber engine.

.MyFeatureIT.java
[source,java]
----
import org.junit.platform.suite.api.ConfigurationParameter;
import org.junit.platform.suite.api.IncludeEngines;
import org.junit.platform.suite.api.SelectPackages;
import org.junit.platform.suite.api.Suite;

import static io.cucumber.junit.platform.engine.Constants.GLUE_CLASSES_PROPERTY_NAME;
import static io.cucumber.junit.platform.engine.Constants.PLUGIN_PROPERTY_NAME;

@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_CLASSES_PROPERTY_NAME, value = "com.example.EchoSteps")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {
}
----

The test case above uses the *Cucumber* JUnit Platform suite support. In addition to that we give some options to the Cucumber execution.
The `cucumber.glue.classes` parameter registers the step definition class *EchoSteps* directly, so Cucumber does not have
to scan a glue package for step definitions. You can also use a glue package with `cucumber.glue` as described in
<<cucumber-glue-discovery,glue discovery>>.

NOTE: `cucumber.glue.classes` is experimental in Cucumber 8 (`@API(status = EXPERIMENTAL, since = "8.0.0")`) and may
change in later 8.x releases. The stable alternative is a narrow `cucumber.glue` package as described in
<<cucumber-glue-discovery,glue discovery>>.

In case you want to have the usual Citrus test results reported you can add the special Citrus reporter implementation
`org.citrusframework.cucumber.CitrusReporter`. This class is responsible for printing the Citrus test summary. This reporter
extends the default Cucumber reporter so the default Cucumber report summary is also printed to the console.
Citrus starts and finishes its test suite with Cucumber `BeforeAll` and `AfterAll` hooks, see <<cucumber-suite-hooks,suite hooks>>.
Some Cucumber report plugins need Jackson on the classpath, see <<cucumber-report-plugins,report plugins and Jackson>>.

That completes the suite class configuration. Now we are able to add feature stories and step definitions to the package
of our test *MyFeatureIT*. Cucumber picks up the feature files in that test package and runs them with the registered
step definition class. So let's write a feature story *echo.feature* right next to the *MyFeatureIT* test class.

.echo.feature
[source,gherkin]
----
Feature: Echo service

  Scenario: Say hello
    Given My name is Citrus
    When I say hello to the service
    Then the service should return: "Hello, my name is Citrus!"

  Scenario: Say goodbye
    Given My name is Citrus
    When I say goodbye to the service
    Then the service should return: "Goodbye from Citrus!"
----

As you can see this story defines two scenarios with the Gherkin *Given-When-Then* syntax. Now we need to add step definitions
that glue the story description to Citrus test actions. Let's do this in a new class *EchoSteps* .

.EchoSteps.java
[source,java]
----
public class EchoSteps {

    @CitrusResource
    private TestCaseRunner runner;

    @Given("^My name is (.*)$")
    public void my_name_is(String name) {
        runner.variable("username", name);
    }

    @When("^I say hello.*$")
    public void say_hello() {
        runner.when(
                send("echoEndpoint")
                    .message()
                    .type(MessageType.PLAINTEXT)
                    .body("Hello, my name is ${username}!"));
    }

    @When("^I say goodbye.*$")
    public void say_goodbye() {
        runner.when(
                send("echoEndpoint")
                    .message()
                    .type(MessageType.PLAINTEXT)
                    .body("Goodbye from ${username}!"));
    }

    @Then("^the service should return: \"([^\"]*)\"$")
    public void verify_return(final String body) {
        runner.then(
                receive("echoEndpoint")
                    .message()
                    .type(MessageType.PLAINTEXT)
                    .body(body));
    }
}
----

The step definition class is a normal POJO that uses some annotations such as `@CitrusResource` annotated `TestCaseRunner`.
The Citrus backend injects the test runner instance at runtime.

The step definition contains normal @Given, @When or @Then annotated methods that match the scenario descriptions in our
feature file. Cucumber will automatically find matching methods and execute them. The methods add test actions to the test runner
as we used to do in normal Java DSL tests.

That is a first combination of Citrus and Cucumber BDD. The feature file gets translated into step implementations that
use Citrus test action runner Java API to run integration tests with behavior driven development.

[[cucumber-junit4-migration]]
=== Migrating from the Cucumber JUnit 4 runner

Citrus no longer uses the deprecated Cucumber JUnit 4 runner integration. It uses the JUnit Platform engine instead.
The JUnit Platform engine ignores `@CucumberOptions`. When the project runs on the JUnit Platform,
`@RunWith(Cucumber.class)` is only executed by the JUnit Vintage engine. Once the JUnit Vintage engine is removed, the
feature files silently stop running.

The migration has three parts: replace the Maven dependencies, replace the runner annotations with JUnit Platform suite
annotations, and move the `cucumber.properties` settings to `junit-platform.properties`.

.Migrate the Maven dependencies
[source,xml]
----
<!-- Remove the JUnit 4 runner integration -->
<dependency>
  <groupId>io.cucumber</groupId>
  <artifactId>cucumber-junit</artifactId>
</dependency>
<dependency>
  <groupId>org.junit.vintage</groupId>
  <artifactId>junit-vintage-engine</artifactId>
</dependency>

<!-- Add the JUnit Platform engine and suite support -->
<dependency>
  <groupId>io.cucumber</groupId>
  <artifactId>cucumber-junit-platform-engine</artifactId>
  <version>${cucumber.version}</version>
</dependency>
<dependency>
  <groupId>org.junit.platform</groupId>
  <artifactId>junit-platform-suite</artifactId>
  <version>${junit.platform.version}</version>
</dependency>
----

Keep JUnit 4 and the JUnit Vintage engine only if other tests in the project still need them. The Cucumber JUnit Platform
engine does not require the JUnit Vintage engine.

The following example shows the same suite class before and after the migration. The class name and the `*IT` naming
convention do not change.

.Before: Cucumber JUnit 4 runner
[source,java]
----
import io.cucumber.junit.Cucumber;
import io.cucumber.junit.CucumberOptions;
import org.junit.runner.RunWith;

@RunWith(Cucumber.class)
@CucumberOptions(
    features = "classpath:com/example",
    glue = { "com.example", "org.citrusframework.cucumber" },
    tags = "@smoke",
    plugin = { "pretty", "org.citrusframework.cucumber.CitrusReporter" })
public class MyFeatureIT {
}
----

.After: JUnit Platform suite
[source,java]
----
import org.junit.platform.suite.api.ConfigurationParameter;
import org.junit.platform.suite.api.IncludeEngines;
import org.junit.platform.suite.api.SelectClasspathResource;
import org.junit.platform.suite.api.Suite;

import static io.cucumber.junit.platform.engine.Constants.FILTER_TAGS_PROPERTY_NAME;
import static io.cucumber.junit.platform.engine.Constants.GLUE_PROPERTY_NAME;
import static io.cucumber.junit.platform.engine.Constants.PLUGIN_PROPERTY_NAME;

@Suite
@IncludeEngines("cucumber")
@SelectClasspathResource("com/example")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example,org.citrusframework.cucumber")
@ConfigurationParameter(key = FILTER_TAGS_PROPERTY_NAME, value = "@smoke")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {
}
----

Use `@IncludeEngines("cucumber")` to run only the Cucumber engine. Without that annotation other JUnit Platform engines
on the test classpath also participate in test discovery. `@SelectClasspathResource` uses slash-separated resource
paths. Use `@SelectPackages` when the feature files are located in the package of the suite class. For feature files
outside the test classpath, use the `cucumber.features` configuration parameter with a file path or URI.

The migrated suite keeps the broad `org.citrusframework.cucumber` glue package of the original runner. After the
migration you can replace it with explicit glue classes as described in <<cucumber-glue-discovery,glue discovery>>.

The following table maps the `@CucumberOptions` attributes to their JUnit Platform counterparts. Put the configuration
parameter either in `@ConfigurationParameter` or in `junit-platform.properties`.

[cols="1,1,2"]
|===
|`@CucumberOptions` |Configuration parameter |Notes

|`features`
|`cucumber.features`
|Prefer `@SelectClasspathResource`, `@SelectClasspathResources`, or `@SelectPackages`.

|`glue`
|`cucumber.glue`
|Comma-separated package or class names.

|`extraGlue`
|`cucumber.glue`
|Append the extra packages to the same comma-separated value.

|`plugin`
|`cucumber.plugin`
|Plugin names and order stay the same, including `org.citrusframework.cucumber.CitrusReporter`.

|`tags`
|`cucumber.filter.tags`
|Standard Cucumber tag expression.

|`name`
|`cucumber.filter.name`
|Regular expression matched against scenario names.

|`monochrome`
|`cucumber.ansi-colors.disabled`
|Use `true` to disable colors.

|`dryRun`
|`cucumber.execution.dry-run`
|Use `true` to verify step matching without executing steps.

|`snippets`
|`cucumber.snippet-type`
|Snippet naming style, for example `camelcase` or `underscore`.

|`publish`
|`cucumber.publish.enabled`
|Use `false` to disable publishing the Cucumber report.
|===

The JUnit Platform engine does not read `cucumber.properties`. Keep the `cucumber.properties` file only when the tests
are also executed by the Citrus test engine or the Cucumber command line. For the JUnit Platform engine, move the same
`cucumber.*` keys to `junit-platform.properties` or pass them as JUnit Platform configuration parameters.

Maven Surefire and Failsafe must use the JUnit Platform provider. Surefire and Failsafe 3.x select that provider
automatically when the Cucumber JUnit Platform engine is on the test classpath. Remove an explicit `surefire-junit4`
provider dependency if the project declares one. The `*IT` class name convention still works with Failsafe.

Run the suite class as a JUnit Platform test in the IDE or with Maven. It is no longer executed as a JUnit 4 test.

Custom `CitrusBackend` or `CitrusSpringBackend` subclasses should override
`loadGlue(Glue, GlueDiscoveryRequest)` instead of the deprecated `loadGlue(Glue, List<URI>)` method. The deprecated
method is still called by the default implementation for backwards compatibility, but it will be removed when Cucumber
drops the deprecated interface method.

[[cucumber-glue-discovery]]
=== Glue discovery

Cucumber needs to know which classes provide step definitions, hooks and parameter types. You can register the glue
classes explicitly or let Cucumber scan glue packages.

[cols="1,2"]
|===
|Configuration parameter |Effect

|`cucumber.glue.classes`
|Comma-separated fully qualified class names. Cucumber registers exactly these glue classes and does not scan a package for them.

|`cucumber.glue`
|Comma-separated package names. Cucumber scans the packages and their sub-packages for glue classes.

|`cucumber.glue.included-class-name-pattern`
|Regular expression. While scanning a glue package, Cucumber keeps only the classes whose fully qualified name matches.

|`cucumber.glue.excluded-class-name-pattern`
|Regular expression. While scanning a glue package, Cucumber drops the classes whose fully qualified name matches.

|`cucumber.glue.hint.enabled`
|Use `false` to disable the glue hint.

|`cucumber.glue.hint.threshold`
|Threshold that controls when Cucumber prints the glue hint.
|===

NOTE: The `cucumber.glue.classes`, `cucumber.glue.included-class-name-pattern`, `cucumber.glue.excluded-class-name-pattern`
and `cucumber.glue.hint.*` parameters are experimental in Cucumber 8 and may still change in later 8.x releases. Scanning a
glue package with `cucumber.glue` is the stable alternative.

Explicit glue classes are the fastest option and also work well with GraalVM native images, because the step classes do
not have to be discovered with classpath scanning. The list must contain every glue class the features use, including
your own step classes and any predefined Citrus step classes.

.Explicit glue classes
[source,java]
----
@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_CLASSES_PROPERTY_NAME, value = "com.example.EchoSteps,com.example.GreetingSteps")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {
}
----

When you prefer package scanning, keep the glue package as narrow as possible. The class name patterns narrow the scan
further. They only apply to classes found by scanning a `cucumber.glue` package, not to classes listed in
`cucumber.glue.classes`.

.Glue package with class name filter
[source,java]
----
@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example")
@ConfigurationParameter(key = GLUE_INCLUDED_CLASS_NAME_PATTERN_PROPERTY_NAME, value = "^com\\.example\\..*Steps$")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {
}
----

When a glue package scan loads many classes, Cucumber prints a hint that recommends explicit glue classes or class name
filters. Resolve the hint by listing the glue classes in `cucumber.glue.classes`, by using a narrower `cucumber.glue`
package, or by adding an included or excluded class name pattern. Set `cucumber.glue.hint.enabled=false` to silence it.

All of these parameters work in `@ConfigurationParameter` and in `junit-platform.properties`.

.junit-platform.properties
[source,properties]
----
cucumber.object-factory=org.citrusframework.cucumber.backend.CitrusObjectFactory
cucumber.glue.classes=com.example.EchoSteps,com.example.GreetingSteps
----

[cols="1,2"]
|===
|File |Read by

|`junit-platform.properties`
|The Cucumber JUnit Platform engine (`@Suite` classes).

|`cucumber.properties`
|The Citrus test engine and the Cucumber command line. The JUnit Platform engine ignores this file.
|===

The `CitrusObjectFactory` creates glue classes through a non-private zero-argument constructor. Public, protected and
package-private glue classes and constructors are supported. A glue class without such a constructor fails with a
`CucumberException` naming the class. When your tests run as a named Java module, open the glue package to Cucumber so
that it can create package-private classes reflectively.

[[cucumber-report-plugins]]
=== Report plugins and Jackson

The Cucumber `json`, `html`, `message`, `timeline` and `usage-json` plugins write JSON and need a Jackson implementation
on the test runtime classpath. Cucumber supports Jackson 3 or Jackson 2. Citrus projects should use Jackson 3.

.Jackson 3 for Cucumber report plugins
[source,xml]
----
<dependency>
  <groupId>tools.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <scope>test</scope>
</dependency>
----

With Jackson 2, add both `com.fasterxml.jackson.core:jackson-databind` and
`com.fasterxml.jackson.datatype:jackson-datatype-jdk8` instead. Without a Jackson implementation these plugins fail with
a `CucumberException` that lists the missing dependencies.

The Citrus termination log reporter (`org.citrusframework.cucumber.report.json.TerminationLogReporter`) always requires Jackson 3
(`tools.jackson.core:jackson-databind`). The `citrus-cucumber` module does not bring Jackson with it, so add the
dependency to your project when you use this reporter.

[[cucumber-suite-hooks]]
=== Suite hooks

Citrus registers two Cucumber static hooks that run once per Cucumber run: `CitrusLifecycleHooks.beforeSuite` as
`BeforeAll` hook and `CitrusLifecycleHooks.afterSuite` as `AfterAll` hook. They run the Citrus before suite and after suite
actions and notify the Citrus test suite listeners. Both hooks use order `10000`, the Cucumber default, and show up with
these names in Cucumber hook messages and reports.

The suite is finished by the `AfterAll` hook, not by the Citrus reporter, so the after suite actions also run when you do
not register `org.citrusframework.cucumber.CitrusReporter`. Your own `@AfterAll` hooks with a lower order run after the
Citrus suite has finished.

The `BeforeAll` hook does not create a Citrus instance. When no instance exists yet, the suite starts as soon as the
object factory creates one. This keeps the Spring object factory in charge of creating the Citrus instance from the
Spring application context.

[[cucumber-parallel-execution]]
=== Parallel execution

The Cucumber JUnit Platform engine can run scenarios in parallel. Enable it with the Cucumber configuration parameters on
the suite class or in `junit-platform.properties`.

.Parallel scenarios
[source,java]
----
@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example")
@ConfigurationParameter(key = PARALLEL_EXECUTION_ENABLED_PROPERTY_NAME, value = "true")
@ConfigurationParameter(key = PARALLEL_CONFIG_STRATEGY_PROPERTY_NAME, value = "fixed")
@ConfigurationParameter(key = PARALLEL_CONFIG_FIXED_PARALLELISM_PROPERTY_NAME, value = "4")
@ConfigurationParameter(key = PARALLEL_CONFIG_FIXED_MAX_POOL_SIZE_PROPERTY_NAME, value = "4")
public class MyFeatureIT {
}
----

.junit-platform.properties
[source,properties]
----
cucumber.execution.parallel.enabled=true
cucumber.execution.parallel.config.strategy=fixed
cucumber.execution.parallel.config.fixed.parallelism=4
cucumber.execution.parallel.config.fixed.max-pool-size=4
----

Each scenario still gets its own Citrus test case, test context and test variables, and both Java and XML step
definitions can run in parallel. All scenarios share one Citrus
instance, so the endpoints, components and before/after suite actions configured in the Citrus context are shared as well.
The <<cucumber-suite-hooks,suite hooks>> still run once per Cucumber run.

Keep the following in mind when you run scenarios in parallel:

* Scenarios that send and receive on the same endpoint at the same time can consume each other's messages. Use separate
endpoints or message selectors and correlation so that each scenario receives its own messages.
* Step definition classes are created per scenario, but static fields in your glue classes are shared between threads.
* The static `CitrusObjectFactory.instance()` and `CitrusSpringObjectFactory.instance()` accessors are deprecated. Cucumber
creates one object factory per thread, so the static reference may belong to another thread. Inject Citrus resources
with `@CitrusResource` and `@CitrusFramework` instead.
* Log output of parallel scenarios is interleaved.

=== DocString and DataTable on one step

A Gherkin step can carry a DocString and a DataTable at the same time. The DocString comes first, then the DataTable.
The Java step definition receives both as its last two arguments in that order.

.DocString and DataTable
[source,gherkin]
----
Given message
  """
  Hello Citrus
  """
  | operation | greeting |
  | language  | en       |
----

.Step definition
[source,java]
----
@Given("^message$")
public void message(String body, DataTable headers) {
    runner.given(createVariable("body", body));
    headers.asMap().forEach((name, value) -> runner.given(createVariable(name, value)));
}
----

XML step templates pass every argument as `String`, so use a Java step definition for DataTable arguments.

[[cucumber-xml-steps]]
=== Cucumber XML steps

The previous section handled glue code in Java in form of step definitions accessing the Java test runner fluent API.
This chapter deals with the same concept with just XML configuration.

Citrus provides a separate configuration namespace and schema definition for Cucumber related step definitions. Include
this namespace into your Spring configuration in order to use the Citrus Cucumber configuration elements.

.Spring bean configuration schema
[source,xml]
----
<spring:beans xmlns:spring="http://www.springframework.org/schema/beans"
     xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
     xmlns="http://www.citrusframework.org/schema/cucumber/testcase"
     xsi:schemaLocation="
         http://www.springframework.org/schema/beans
         http://www.springframework.org/schema/beans/spring-beans.xsd
         http://www.citrusframework.org/schema/cucumber/testcase
         http://www.citrusframework.org/schema/cucumber/testcase/citrus-cucumber-testcase.xsd">

    [...]

</spring:beans>
----

The JUnit Platform suite class itself does not change. We still use the Cucumber JUnit Platform suite support with some
options specific to Citrus:

.MyFeatureIT.java
[source,java]
----
@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {
}
----

The feature file with its Gherkin scenarios does also not change:

.echo.feature
[source,gherkin]
----
Feature: Echo service

  Scenario: Say hello
    Given My name is Citrus
    When I say hello to the service
    Then the service should return: "Hello, my name is Citrus!"

  Scenario: Say goodbye
    Given My name is Citrus
    When I say goodbye to the service
    Then the service should return: "Goodbye from Citrus!"
----

In the feature package *my.company.features* we add a new XML file `EchoSteps.xml` that holds the new XML step definitions:

.EchoSteps.xml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<spring:beans xmlns:citrus="http://www.citrusframework.org/schema/testcase"
      xmlns:spring="http://www.springframework.org/schema/beans"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xmlns="http://www.citrusframework.org/schema/cucumber/testcase"
      xsi:schemaLocation="http://www.springframework.org/schema/beans
              http://www.springframework.org/schema/beans/spring-beans.xsd
              http://www.citrusframework.org/schema/cucumber/testcase
              http://www.citrusframework.org/schema/cucumber/testcase/citrus-cucumber-testcase.xsd">

  <step given="^My name is (.*)$" parameter-names="username">
    <citrus:create-variables>
      <citrus:variable name="username" value="${username}"/>
    </citrus:create-variables>
  </step>

  <step when="^I say hello.*$">
    <citrus:send endpoint="echoEndpoint">
      <citrus:message type="plaintext">
        <citrus:data>Hello, my name is ${username}!</citrus:data>
      </citrus:message>
    </citrus:send>
  </step>

  <step when="^I say goodbye.*$">
    <citrus:send endpoint="echoEndpoint">
      <citrus:message type="plaintext">
        <citrus:data>Goodbye from ${username}!</citrus:data>
      </citrus:message>
    </citrus:send>
  </step>

  <step then="^the service should return: &quot;([^&quot;]*)&quot;$" parameter-names="body">
    <citrus:receive endpoint="echoEndpoint">
      <citrus:message type="plaintext">
        <citrus:data>You just said: ${body}</citrus:data>
      </citrus:message>
    </citrus:receive>
  </step>

</spring:beans>
----

The above step definition uses pure XML actions. Citrus will automatically read the step definition and add those to the
Cucumber runtime. Following from that the step definitions are executed when matching a statement in the feature story.

The XML step files follow a naming convention. Citrus will look for all files located in the feature package with name
pattern `\\**/**.Steps.xml` and load those definitions when Cucumber starts up.

The XML steps are able to receive parameters from the Gherkin regexp matcher. The parameters are passed to the step as
test variable. The parameter names get declared in the optional attribute `parameter-names`. In the step definitions you
can use the parameter names as test variables.

NOTE: The test variables are visible in all upcoming steps, too. This is because the test variables are global by default.
If you need to set local state for a step definition you can use another attribute `global-context` and set it to `false`
in the step definition. This way all test variables and parameters are only visible in the step definition. Other steps
will not see the test variables.

NOTE: Another notable thing is the XML escaping of reserved characters in the pattern definition. You can see that in the
last step where the *then* attribute is escaping quotation characters.

.Escape reserved characters
[source,xml]
----
<step then="^the service should return: &quot;([^&quot;]*)&quot;$" parameter-names="body">
...
</step>
----

We have to do this because otherwise the quotation characters will interfere with the XML syntax in the attribute.

This completes the description of how to add XML step definitions to the cucumber BDD tests.

[[cucumber-spring]]
=== Cucumber Spring support

Cucumber provides support for Spring dependency injection in step definition classes. The Cucumber Spring capabilities
are included in a separate module. So first of all we have to add this dependency to our project:

[source,xml]
----
<dependency>
  <groupId>io.cucumber</groupId>
  <artifactId>cucumber-spring</artifactId>
  <version>${cucumber.version}</version>
</dependency>
----

The Citrus Cucumber extension has to handle things different when Cucumber Spring support is enabled. Therefore we use
another object factory implementation that also support Cucumber Spring features. Change the object factory property in
*junit-platform.properties* to the following:

.junit-platform.properties
[source,properties]
----
cucumber.object-factory=org.citrusframework.cucumber.backend.spring.CitrusSpringObjectFactory
----

Now we are ready to add *@Autowired* Spring bean dependency injection to step definition classes:

.EchoSteps.java
[source,java]
----
@ContextConfiguration(classes = CitrusSpringConfig.class)
public class EchoSteps {
    @Autowired
    private Endpoint echoEndpoint;

    @CitrusResource
    protected TestDesigner designer;

    @Given("^My name is (.*)$")
    public void my_name_is(String name) {
        designer.variable("username", name);
    }

    @When("^I say hello.*$")
    public void say_hello() {
        designer.send(echoEndpoint)
            .messageType(MessageType.PLAINTEXT)
            .payload("Hello, my name is ${username}!");
    }

    @When("^I say goodbye.*$")
    public void say_goodbye() {
        designer.send(echoEndpoint)
            .messageType(MessageType.PLAINTEXT)
            .payload("Goodbye from ${username}!");
    }

    @Then("^the service should return: \"([^\"]*)\"$")
    public void verify_return(final String body) {
        designer.receive(echoEndpoint)
            .messageType(MessageType.PLAINTEXT)
            .payload("You just said: " + body);
    }
}
----

As you can see we used Spring autowiring mechanism for the *echoEndpoint* field in the step definition. Also be sure to
define the *@ContextConfiguration* annotation on the step definition. The Cucumber Spring support loads the Spring application
context and takes care of dependency injection. We use the Citrus *CitrusSpringConfig* Java configuration because this is
the main entrance for Citrus test cases. You can add custom beans and further Spring related configuration to this Spring
application context. If you want to add more beans for autowiring do so in the Citrus Spring configuration. Usually this
is the default *citrus-context.xml* which is automatically loaded.

Of course, you can also use a custom Java Spring configuration class here. Please be sure to always import the Citrus
Spring Java configuration classes, too.

As usual, we are able to use *@CitrusResource* annotated *TestCaseRunner* fields for building the Citrus integration test
logic. With this extension you can use the full Spring testing power in your tests in particular dependency injection and
also transaction management for data persistence tests.

[[citrus-step-definitions]]
=== Predefined step definitions

Citrus provides a set of predefined step implementations for typical integration test scenarios that you can use out-of-the-box in a Cucumber feature.

You can basically define send/receive operations and many other predefined steps to leverage Citrus functionality such as endpoints and test
actions. As these steps are predefined in Citrus you just need to add the step as a line in your feature stories. The step definitions with
the glue to test actions is handled automatically when running Citrus with Cucumber.

If you want to enable predefined steps support in your test you need to include the Citrus Cucumber steps module as a Maven dependency.

.Citrus Cucumber step module dependency
[source,xml]
----
<dependency>
  <groupId>org.citrusframework</groupId>
  <artifactId>citrus-cucumber-core</artifactId>
  <version>${citrus.version}</version>
  <scope>test</scope>
</dependency>
----

After that you need to register the predefined step classes as glue in your test class like this:

.Include Citrus steps
[source,java]
----
@Suite
@IncludeEngines("cucumber")
@SelectPackages("com.example")
@ConfigurationParameter(key = GLUE_CLASSES_PROPERTY_NAME, value = "org.citrusframework.cucumber.steps.core.StandardSteps,"
        + "org.citrusframework.cucumber.steps.core.MessagingSteps,"
        + "org.citrusframework.cucumber.steps.core.EndpointSteps,"
        + "org.citrusframework.cucumber.steps.core.ComponentSteps")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty,org.citrusframework.cucumber.CitrusReporter")
public class MyFeatureIT {

}
----

Instead of writing the glue code on our own in step definition classes we register the predefined Citrus step classes of the
`citrus-cucumber-core` module as glue. Add your own step classes to the same list when the features also use them. Once you
have done this you can use predefined steps without having to write any glue code in Java.

Each step module keeps its step classes in the package `org.citrusframework.cucumber.steps.<module>`, for example
`org.citrusframework.cucumber.steps.http`. You can use such a package as `cucumber.glue` and narrow it with the class name
patterns described in <<cucumber-glue-discovery,glue discovery>>.

TIP: To load the predefined steps of every step module on the classpath, use the broad glue package
`org.citrusframework.cucumber` instead, for example `@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example,org.citrusframework.cucumber")`.
This scans all Citrus step packages and therefore takes longer to start.

[source,gherkin]
----
Feature: Hello World

  Scenario: Print Hello World
    Given variable text="Hello World!"
    Then print 'You just said: ${text}'

----

The feature uses the default predefined steps `Given variable <name>="<value>"` and `Then print '<output>'` provided by Citrus.

The Citrus framework provides many different modules serving many different aspects of integration testing.
You can add those steps with modular dependencies in Maven.
See the following modules with predefined steps provided by Citrus:

.Citrus Cucumber step modules
|===
|Module |Description

| citrus-cucumber-core
| Standard steps such as test variables, sleep/delay, log/print, ...

| citrus-cucumber-http
| Http steps for client and server side communication

| citrus-cucumber-openapi
| Load Open API specifications and invoke/verify operations with generated test data

| citrus-cucumber-kubernetes
| Manage Kubernetes resources (e.g. pods, deployments, custom resources)

| citrus-cucumber-knative
| Steps to connect with Knative eventing and messaging

| citrus-cucumber-jms
| Send/receive steps via JMS queues/topics

| citrus-cucumber-kafka
| Steps to publish/subscribe on Kafka messaging

| citrus-cucumber-jdbc
| Steps to connect to relational databases

| citrus-cucumber-camel
| Steps to access Apache Camel components and Camel routes

| citrus-cucumber-selenium
| Run UI tests with Selenium using Selenium grid or standalone containers

| citrus-cucumber-groovy
| Leverage Groovy scripts as Citrus endpoint and component configuration

| citrus-cucumber-testcontainers
| Manage Testcontainers instances with starting/stopping databases, message brokers and many more

|===

Once again it is important to understand that the predefined step definitions included in these modules can be used out-of-the-box.
You can just start to write BDD features in Gherkin syntax that trigger these predefined steps.


TIP: If you want to include all available step definitions into your project at once you can use the `citrus-cucumber-all` module dependency.

.Include all Citrus Cucumber steps
[source,xml]
----
<dependency>
  <groupId>org.citrusframework</groupId>
  <artifactId>citrus-cucumber-all</artifactId>
  <version>${citrus.version}</version>
  <scope>test</scope>
</dependency>
----

Read more about the individual step implementations and their functionality in xref:tools-cucumber-steps[Tools - Citrus Cucumber steps].
